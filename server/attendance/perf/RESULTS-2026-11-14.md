## Môi trường

- Máy Windows 11, Docker Desktop 29.6.1 (WSL2, kernel 6.6.114.1).
- Docker được cấp **4 CPU** và **5,8 GiB RAM** cho toàn bộ container.
- Giới hạn mỗi container: API 2 CPU / 2 GiB (mỗi instance); PostgreSQL
  2 CPU / 2 GiB; Redis 1 CPU / 512 MiB.
- k6 v2.3.0 chạy trong container trên cùng máy với server.
- Fixture: mỗi sinh viên có JWT và device ID riêng. Script `prepare` tạo sẵn
  một phiên đang mở và nạp roster vào Redis, nên phép đo chỉ bao phủ API
  check-in.
- Hai kịch bản tải:
  - **rate**: 1.000 check-in rải đều trong 60 giây (`constant-arrival-rate`).
  - **burst**: 1.000 VU, mỗi VU một sinh viên, chờ 2 giây cho mọi VU khởi tạo
    rồi gửi đồng thời (`per-vu-iterations`), mô phỏng cả lớp bấm điểm danh
    ngay khi phiên mở.

**Lưu ý:** tổng giới hạn CPU của các container (2 API × 2 + Postgres 2 +
Redis 1) vượt 4 CPU thật, và k6 dùng chung máy. Ở cấu hình 2 instance, các
container tranh CPU với nhau, nên kết quả thiên về bi quan.

## 1. Kịch bản rate — 1.000 check-in trong 60 giây

| Phiên bản | Đường gọi | Chấp nhận | Lỗi HTTP | Dropped | p95 | max |

| Bản gốc | Thẳng API | 1.000 | 0 | 0 | 11,73 ms | 86,24 ms |

Bản mới qua nginx: `proxy_first_byte` p95 = 9 ms, `upstream_header` p95 =

## 2. Kịch bản burst — 1.000 check-in đồng thời

### 2.1. Phát hiện lỗi tràn listen backlog

Lần chạy burst đầu tiên qua nginx (bản mới, chưa có `d02ddd1`):

| Cấu hình | p95 `http_req_duration` | `upstream_connect` p90 / p95 | `ListenOverflows` trong container API |
|---|---:|---:|---:|
| 1 instance | 1,39 s | 1,03 s / 1,03 s | — |
| 2 instance | 1,45 s | 1,03 s / 1,04 s | — |
| 1 instance (đo lại) | 1,47 s | 1,02 s / 1,02 s | **907** |

Thời gian nginx mở kết nối tới API dừng đúng ở khoảng 1 giây, bằng thời gian
chờ gửi lại SYN của TCP. Bộ đếm `ListenOverflows = 907` xác nhận kernel đã bỏ
907 kết nối, do Node mặc định backlog 511 trong khi `net.core.somaxconn` của
container là 4096. Thêm instance không cải thiện được, vì mỗi instance đều
tràn hàng đợi theo cách này.

Sau khi tăng backlog lên 4096 (`d02ddd1`), 1 instance qua nginx:

| Chỉ số | Trước | Sau |
|---|---:|---:|
| `ListenOverflows` | 907 | **0** |
| `upstream_connect` p95 | 1,02 s | **32 ms** |
| p95 `http_req_duration` | 1,47 s | 1,40 s |

Hết độ trễ do mở kết nối, nhưng p95 tổng vẫn khoảng 1,4 s ở lần đo này. Phần
thời gian giờ nằm ở `upstream_header` (API xử lý): một tiến trình Node đơn
luồng phải xếp hàng 1.000 request.

### 2.2. Mở rộng ngang — 2 instance sau nginx

| Cấu hình (bản mới, đã sửa backlog) | p95 | Ngưỡng 1 s | `upstream_connect` p95 | Lỗi HTTP |
|---|---:|---|---:|---:|
| 1 instance qua nginx | 1,40 s | ✗ | 32 ms | 0 |
| **2 instance qua nginx** | **936 ms** | ✓ | 32 ms | 0 |

### 2.3. So sánh với bản gốc cùng điều kiện (1 instance)

Mỗi cấu hình chạy 2 lần (`run1 / run2`). `iteration_duration` gồm 2 s chờ
khởi tạo VU.

| Phiên bản | Đường gọi | `http_req_duration` p95 | `http_req_connecting` p95 | `iteration_duration` p95 |
|---|---|---:|---:|---:|
| Bản gốc | Thẳng API | 903 ms / 912 ms | — / 117 ms | — / 3,06 s |
| Bản mới | Thẳng API | 984 ms / 869 ms | 126 ms / 103 ms | 3,18 s / 3,01 s |
| Bản mới | Qua nginx | 998 ms / 1,02 s | 74 ms / 129 ms | 3,18 s / 3,20 s |

`ListenOverflows` của bản gốc khi k6 gọi thẳng API là 0: k6 mở kết nối chậm
hơn nginx nên không làm tràn backlog 511.

Ở mọi lần chạy burst, cả 1.000 request được chấp nhận (`VALID`), không có lỗi
HTTP, và Redis có đủ 1.000 bản ghi `present`.

### 2.4. Nhận xét

- Với 1 instance, bản mới và bản gốc tương đương. Chênh lệch giữa các lần
  chạy (khoảng ±100 ms) lớn hơn chênh lệch giữa hai phiên bản.
- nginx không phải nút cổ chai. Qua nginx và gọi thẳng chênh nhau không quá
  vài chục ms, trong khoảng dao động. Con số 1,4 s ở mục 2.1–2.2 nhiều khả
  năng rơi vào lần burst đầu tiên sau khi container vừa khởi động lại
  (JIT/pool chưa ấm), nhưng chưa được kiểm chứng riêng.
- Cache session không cải thiện kịch bản burst, vì nút cổ chai là CPU của
  Node (xác thực JWT, validate request) chứ không phải PostgreSQL.
- Chịu được burst trong ngưỡng 1 s đòi hỏi nhiều instance. Điều này khả thi
  nhờ nginx, việc tách migration khỏi service API, và giới hạn pool DB cho
  từng instance.

## 3. Flush xuống PostgreSQL

Sau khi phiên điểm danh của lần burst 2 instance (session 10) đóng và job
flush chạy, kết quả `VERIFY_PHASE=after-flush`:

```json
{"sessionId":10,"phase":"after-flush","expected":1000,"buffer":0,"bufferPresent":0,"postgres":1000,"postgresPresent":1000}
```

Toàn bộ 1.000 bản ghi `present` đã được ghi xuống PostgreSQL và buffer Redis
đã trống.

## 4. Kiểm thử tranh chấp (race)

Script `check-in-race.js`, mỗi lần một fixture 3 sinh viên mới:

- Hai sinh viên khác nhau gửi đồng thời với cùng một device ID.
- Một sinh viên gửi đồng thời hai request với hai device ID khác nhau.

| Cấu hình | Số lần | Một thiết bị một sinh viên | Lý do `DUPLICATE_DEVICE` | Một lượt check-in mỗi sinh viên |
|---|---:|---|---|---|
| 1 instance, thẳng API | 3 | ✓ 3/3 | ✓ 3/3 | ✓ 3/3 |
| 2 instance, qua nginx | 3 | ✓ 3/3 | ✓ 3/3 | ✓ 3/3 |

Phản hồi thực tế cho hai request đồng thời của cùng một sinh viên:

```
201 {"success":true,"data":{"status":"VALID"}}
409 {"success":false,"code":"ATTENDANCE_REVIEW_ALREADY_CHECKED_IN","message":"Đã điểm danh rồi"}
```

Lần chạy đầu báo trượt 6/6 ở mục "một lượt check-in mỗi sinh viên". Nguyên
nhân là script so với mã lỗi cũ `ALREADY_CHECKED_IN`, đã được đổi thành
`ATTENDANCE_REVIEW_ALREADY_CHECKED_IN` từ commit `77e238a`. Server xử lý
đúng; script đã được sửa ở `89013f4`.

Ở cấu hình 2 instance, chưa xác nhận được hai request đồng thời có rơi vào
hai instance khác nhau hay không. Kết quả không phụ thuộc điều đó, vì chống
trùng là một lệnh Lua nguyên tử trên Redis dùng chung.

## 6. Timeout request phía mobile (`9fecba0`)

`FetchHttpClient` (dùng chung cho mobile và dashboard) đã có `AbortController`
30 s từ trước (`3e6a7e4`), nhưng khi hết giờ chỉ ném `AbortError` thô. Hậu
quả khi server quá tải: màn hình điểm danh báo chung chung "Không thể thực
hiện điểm danh", còn màn hình đăng nhập báo **sai mật khẩu**. Sau thay đổi,
client ném `ApiError` có mã riêng và màn hình hiển thị lời nhắc thử lại.

Kiểm thử bằng server HTTP cục bộ, timeout rút xuống 300 ms:

| Tình huống | `code` | `status` | Thời gian | Thử lại được | Thông báo |
|---|---|---:|---:|---|---|
| Server không trả lời | `REQUEST_TIMEOUT` | 0 | 315 ms | ✓ | Máy chủ phản hồi quá lâu. Vui lòng thử lại. |
| nginx trả 502 dạng HTML | `UNKNOWN_ERROR` | 502 | 10 ms | ✓ | Máy chủ đang bận. Vui lòng thử lại sau ít phút. |
| Cổng bị từ chối kết nối | `NETWORK_ERROR` | 0 | 1 ms | ✓ | Không kết nối được tới máy chủ… |
| Lỗi nghiệp vụ 409 | `CONFLICT` | 409 | 3 ms | ✗ | Giữ nguyên thông báo từ server |
| Thành công | — | 200 | — | — | — |

Typecheck `mobile-client` và `admin-dashboard` đều pass. Chưa thử trên thiết
bị thật.

Còn tồn tại: khi mở app, `restoreAuth` gặp bất kỳ lỗi nào (kể cả timeout) đều
xoá token, nên sinh viên bị đăng xuất nếu server quá tải đúng lúc mở app.
Sửa việc này cần thay đổi cách tính `isSignedIn`, nên để lại thành việc
riêng.

## 7. Health endpoint kiểm tra PostgreSQL và Redis (`4aa73c8`)

`GET /health` chạy `SELECT 1` và `PING`, mỗi phép kiểm tra tối đa 2 s (nhỏ
hơn timeout 3 s của Docker healthcheck), trả 503 `SERVICE_UNAVAILABLE` kèm
tên phụ thuộc bị lỗi. Healthcheck Docker của `api` và `/healthz` của nginx
chuyển từ `GET /` (chỉ chứng minh tiến trình Node còn sống) sang endpoint
này. Không mang theo phần thông tin hệ thống, metrics Prometheus và alert từ
nhánh Phước.

Kiểm thử trên stack perf (2 instance sau nginx), gọi `GET /healthz`:

| Tình huống | HTTP | Thời gian | Body |
|---|---:|---:|---|
| Đủ PostgreSQL và Redis | 200 | 10 ms | `{"status":"ok","checks":{"database":"up","redis":"up"}}` |
| Dừng Redis | 503 | 2,02 s | `Không kết nối được: redis` |
| Dừng thêm PostgreSQL | 503 | 2,01 s | `Không kết nối được: database, redis` |
| Khởi động lại cả hai (sau ~15 s) | 200 | 14 ms | `ok` |

Trong lúc dừng, Docker ghi nhận healthcheck thất bại liên tiếp
(`FailingStreak = 3` sau ~15 s; container chuyển `unhealthy` sau 20 lần,
tức ~100 s). Sau khi PostgreSQL và Redis chạy lại, Prisma và ioredis tự kết
nối lại, `FailingStreak` về 0, không cần khởi động lại API.

Thời gian 2 s khi lỗi là do timeout của phép kiểm tra: khi mất kết nối,
ioredis giữ lệnh trong hàng đợi chờ reconnect thay vì báo lỗi ngay.

Unit test: thêm 3 test cho `HealthService` (đủ phụ thuộc, một phụ thuộc lỗi,
một phụ thuộc không phản hồi). Toàn bộ `jest`: 20 suite pass, 1 bỏ qua;
**102 test pass**, 3 bỏ qua.

Giới hạn: nginx bản open source không có active health check, nên `/healthz`
chỉ phục vụ healthcheck Docker. nginx vẫn chỉ loại instance khỏi upstream
khi kết nối lỗi (`max_fails=3`). Compose không tự khởi động lại container
`unhealthy`.

## Phạm vi và giới hạn

- Đây là phép đo hot path check-in trên một máy, với giới hạn Docker cố
  định. Không suy diễn trực tiếp sang VPS hoặc phần cứng khác.
- Fixture bỏ qua luồng tạo phiên và khởi tạo roster qua API. Hai luồng này
  cần được đo riêng (khởi tạo roster hiện ghi Redis lần lượt từng sinh viên).
- Mỗi cấu hình chỉ chạy 1–3 lần; chưa đủ để tính độ lệch chuẩn.
- Chưa đo các API đọc (lịch sử, danh sách phiên), khả năng phục hồi khi
  scheduler sập, và lỗi PostgreSQL trong lúc flush.
- Các cơ chế bảo mật (rate limit, xác thực thiết bị) không nằm trong phạm vi
  đợt đo này.
