# Local Docker performance run — 2026-10-23

## Setup

- Dedicated `gps-attendance-perf` Compose project and volumes.
- API image: `gps-attendance-perf-api:local`, built from the current working tree.
- API: 2 CPU, 2 GiB; PostgreSQL: 2 CPU, 2 GiB; Redis: 1 CPU, 512 MiB.
- Docker inspect confirmed the API container has a 2 CPU quota and
  2,147,483,648 byte memory limit.
- k6 and Docker ran on the same Windows host.
- Each student had a unique JWT and device ID. Fixture setup created an
  already open session and Redis roster; measurements cover the check-in API.

## Results

| Scenario | Requests sent | Accepted | HTTP errors | Dropped iterations | p95 HTTP duration | Data check |
|---|---:|---:|---:|---:|---:|---|
| 5 in 5 seconds | 5 | 5 | 0 | 0 | 39.76 ms | 5 `present` in Redis |
| 1,000 in 60 seconds | 1,000 | 1,000 | 0 | 0 | 5.89 ms | 1,000 `present` in Redis |
| 1,000 in 10 seconds | 1,000 | 1,000 | 0 | 0 | 3.01 ms | 1,000 `present` in Redis; after close, 1,000 `present` in PostgreSQL and Redis buffer empty |

The race check sent two concurrent users with one device ID and two
concurrent requests from one user. All three assertions passed: one user per
device, `DUPLICATE_DEVICE` for the second user, and one accepted check-in per
student with `ALREADY_CHECKED_IN` for the second request.

## Scope of the result

This is a local hot-path result under fixed Docker limits. Fixture creation
bypasses the API session-creation and roster-initialization path; those paths
still need separate load measurements. The k6 generator shares the host with
the server stack. Scheduler crash recovery and database failure during flush
were not exercised. These measurements should not be extrapolated directly
to a VPS or a different host.
